# Simple Tasks — общие правила Claude Code и Codex

Android-приложение: Kotlin, Compose, Room, Glance. Общение с PM — на русском, кратко и понятным языком.
Решение PM от 10.11.2026: одна фича целиком выполняется в одном инструменте; следующая может выполняться в другом.
Общая память — GitHub и файлы репозитория. Контекст другого чата автоматически не передаётся.

## Перед началом

1. Прочитать этот файл, [передачу дел](docs/HANDOFF.md), [требования](SPEC.md) и актуальную часть [архитектуры](docs/ARCHITECTURE.md).
2. Проверить рабочее дерево, текущую ветку, открытые PR и задачу. Незакоммиченные изменения сохранять; не сбрасывать и не перезаписывать чужую работу.
3. Получить актуальный `origin/main`. Новую фичу начинать в новой ветке от него; незавершённую продолжать только по указанным в HANDOFF ветке и коммиту.
4. Найти или создать GitHub Issue, записать исполнителя (Claude Code / Codex), статус «В работе», ожидаемое поведение и критерии готовности.
5. Кратко сообщить план. Если PM уже поручил выполнить этот план, повторное «ок» не требуется; для нового несогласованного объёма сначала согласовать план.
6. При изменении UI сначала показать макет по дизайн-системе и получить согласование PM. Сохранить выбранный вариант и решение в репозитории — [порядок](design/README.md).

Нельзя одновременно выполнять одну фичу в двух инструментах. Постоянных веток «для Claude» и «для Codex» нет.
Не начинать следующую фичу до завершения или явной передачи текущей.

## Передача задач между инструментами

Claude Code может сам поручить фичу Codex: комментарий `@codex …` в её GitHub Issue по шаблону из [docs/CODEX.md](docs/CODEX.md).
Codex работает в облаке ChatGPT по подписке PM, без API-ключей. Фича передаётся целиком; исполнитель в Issue и HANDOFF меняется на Codex,
Claude её больше не правит. Результат Codex — PR; Claude проверяет CI и критерии, правки просит через `@codex` в PR.

## Разработка и качество

- Одна фича/согласованная итерация = одна ветка и один PR. Несколько мелких карточек можно объединять только в согласованную итерацию.
- Сохранять слои domain/data/ui, общую логику для приложения, виджета и уведомлений; не вводить микросервисы ради работы в двух инструментах.
- HEX-цвета и dp вне `designsystem/tokens` запрещены: проверка `checkDesignTokens`.
- Изменение схемы БД — с миграцией Room, экспортом схемы и проверкой сохранения данных. У PM уже есть реальные данные.
- Реальный CSV TickTick и данные пользователя не коммитить. Локальная проверка: `-PticktickCsv=/путь`.
- Изменение UI/токенов/компонентов сопровождается обновлением дизайн-системы и макетов в той же итерации.
- Перед пушем изменений приложения: `./gradlew assembleDebug check recordRoborazziDebug`.
  При недоступной локальной Android-среде явно записать ограничение и выполнить эти проверки через Android CI в PR.
- Для изменений только Markdown и шаблонов: проверить ссылки, согласованность инструкций, сохранность архива и diff; Android CI в PR всё равно должен пройти перед merge.
- Если исправления меняют проверенный код, повторить затронутые проверки. Не выдавать непроведённые проверки за успешные.

## Завершение и передача

1. Обновить требования/архитектуру/макеты/чек-лист по смыслу изменений.
2. Заполнить [HANDOFF](docs/HANDOFF.md): Issue и PR, результат, решения, проверки и ограничения, следующий шаг.
   Для незавершённой работы указать рабочую ветку и последний отправленный коммит.
   Для завершённой — номер PR: его merge commit служит точной точкой передачи; не нужен отдельный коммит только ради записи собственного SHA.
3. Создать PR с результатом, проверками и версией. Обновлять описание по итоговому содержимому; не прикладывать историю чата.
4. После зелёного Android CI и всех обязательных проверок выполнить merge commit (не squash), как ранее согласовано PM.
   Перед merge проверить актуальные head/base и отсутствие конфликтов. Если main изменился, интегрировать его и дождаться проверок итогового состояния.
   Ошибки CI исправить или явно оставить фичу незавершённой.
5. Закрыть выполненные Issues, указать версию/PR; остальные оставить открытыми с точным статусом. Сверить, не решены ли старые связанные задачи.
6. Дождаться результата CI на main, проверить опубликованный APK. Для изменений приложения передать PM APK или доступную ссылку на него и короткий ручной чек-лист.
   Версия: `0.<итерация>.<доработка>`; `versionCode` = число коммитов. Документация сама по себе не требует повышения `versionName`.
7. Сообщить PM итог и оставшиеся проверки на телефоне. Их выполнение не утверждать без результатов PM.
   Следующую фичу начинать со свежего main в новой ветке.

При передаче посреди фичи сначала сохранить и отправить код и HANDOFF, назвать точный коммит и остановить работу в прежнем инструменте.
Если текущая среда не видит незакоммиченную работу другого инструмента, прямо указать это; отсутствие открытого PR не доказывает её отсутствие.

## Среда

В облачной среде для Android-сборки сначала прочитать `tools/cloud-setup.sh` и проверить возможности окружения.
Скрипт настраивает SDK в `/opt/android-sdk`, `local.properties` и зеркало Maven/Robolectric в `~/.gradle`.
Запуск: `bash tools/cloud-setup.sh`, когда нужны сборки и есть соответствующий доступ.
Настройки окружения не коммитить. CI использует Java 21 и полную git-историю для versionCode.
