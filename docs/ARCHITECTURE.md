## 1. Аудит архитектуры

### 1.1. Схема Room

| # | Статус | Проблема | Решение / правило | Итерация |
|---|---|---|---|---|
| R1 | 🔴 | **Даты «на весь день» в UTC.** `due_date` хранится как UTC-мс. Задача «на 13 октября, весь день», сохранённая как полночь по Москве, в другом часовом поясе окажется 12-м или 14-м числом. Спецификация не говорит, *какой* момент времени хранить для all-day. | All-day: хранить полночь календарной даты **в UTC** («плавающая» дата) и сравнивать по календарной дате. Задачи с временем: реальный момент времени (UTC), сравнение по локальной дате пользователя. Всё сравнение дат — в одном классе `DayBoundaries`. | 02 |
| R2 | 🟠 | **Мягкое удаление ломает каскад.** `ON DELETE CASCADE` не срабатывает при `is_deleted = 1`. Удалили список — его задачи остаются «живыми» и всплывают на экране «Все» и в виджете. | Удаление списка/папки — одна транзакция, помечающая `is_deleted` у всех потомков (папка → списки → задачи → пункты). FK оставляем с `RESTRICT`/`NO ACTION` как страховку от «сирот». | 02 |
| R3 | 🟠 | **Нет индекса на `projects.group_id`.** Room выдаст предупреждение (FK-колонка без индекса) и будет сканировать таблицу целиком. | Добавить `idx_projects_group ON projects(group_id, is_deleted)`. `tasks.project_id` и `checklist_items.task_id` уже покрыты существующими индексами. | 02 |
| R4 | 🟠 | **Системный «Inbox» никто не создаёт** и ничто не гарантирует, что он один. Импорт из TickTick создаст второй Inbox. | Создавать Inbox при первом создании БД (callback) с фиксированным ID. Импорт «Inbox» → сливаем в существующий, а не создаём новый. | 02, 03 |
| R5 | 🔴 | **Противоречие:** «физическое удаление запрещено» vs кнопка «полная очистка базы» в Настройках. | Предложение: очистка — единственное разрешённое физическое удаление (пока нет синхронизации), после очистки пересоздаётся Inbox. Нужно подтверждение PM. | 03 |
| R6 | 🟠 | **Повторный импорт = дубликаты.** UUID генерируются заново, повторная загрузка того же CSV удвоит задачи. | Вариант А (рекомендую): колонка `external_id` (TickTick `taskId`) + пропуск уже импортированных. Вариант Б: предупреждение «сначала очистите базу». | 03 |
| R7 | 🟡 | «Сегодня» вычисляется в момент запроса. Если экран открыт через полночь — секции не пересчитаются. | Поток «текущий день» (`TodayTicker`), который переключается в полночь и перезапускает запросы. | 04 |
| R8 | 🟡 | Room-схема должна экспортироваться с первого дня, иначе миграции для v1.1 (теги, синхронизация) будут писаться вслепую. | `exportSchema = true`, папка `app/schemas` в git. | 02 |
| R9 | 🟡 | `updated_at` должен меняться при *любом* изменении, иначе синхронизация v1.1 потеряет правки. | Обновление метки — только в репозитории через общий `Clock`, не в UI. | 02 |

### 1.2. Импорт TickTick (замечания к разделу 6)

| # | Статус | Проблема | Решение |
|---|---|---|---|
| I1 | 🟠 | В реальных выгрузках TickTick перед строкой заголовков обычно идут служебные строки (дата экспорта, версия, легенда статусов). | Парсер ищет строку заголовков, а не берёт первую строку файла. |
| I2 | 🟠 | В выгрузке TickTick есть отдельные колонки `Is All Day`, `Timezone`, `Repeat`, `Is Check list`, `parentId`. Спецификация определяет all-day «по наличию времени» — это ненадёжно. | Использовать `Is All Day` и `Timezone`; `Repeat` сразу класть в `rrule` (поле уже есть). |
| I3 | 🔴 | Формат чек-листов `- [ ]` / `- [x]` не подтверждён реальным файлом; вложенные подзадачи TickTick (`parentId`) в схеме не предусмотрены. | Нужен обезличенный пример CSV от PM. Подзадачи с `parentId` → превращать в пункты чек-листа родителя (предложение). |

## 2. Структура проекта

### 2.1. Модули

MVP — один Gradle-модуль `:app` со строгими пакетами. Изоляция токенов дополнительно защищается автоматической проверкой сборки (`checkDesignTokens`): HEX-цвета (`Color(0x…)`, `#RRGGBB`) вне `designsystem/tokens` валят сборку. Многомодульность (`:core:designsystem`, `:data`, …) — не раньше v1.1, когда появится синхронизация.

### 2.3. Правила зависимостей

```
            ┌──────────────────────────┐
            │  designsystem/tokens     │  (чистый Kotlin)
            └────────┬────────┬────────┘
                     │        │
        ┌────────────▼──┐  ┌──▼─────────────┐
        │ designsystem/ │  │ widget/theme   │
        │ theme (Compose)│ │ (Glance)       │
        └──────┬────────┘  └──┬─────────────┘
               │              │
          ┌────▼────┐    ┌────▼────┐
          │   ui    │    │ widget  │
          └────┬────┘    └────┬────┘
               │              │
               └──────┬───────┘
                      ▼
                ┌──────────┐
                │  domain  │  ◄──── data (реализует интерфейсы)
                └──────────┘
```

- `domain` ни от чего не зависит.
- `ui` и `widget` не знают про `data` (только через интерфейсы `domain`, связывает Hilt).
- `ui` и `widget` не импортируют `designsystem/tokens` напрямую — только через свою тему.

### Итог Итерации 02 — слой данных

| Пункт | Как сделано |
|---|---|
| Таблицы и индексы | Ровно по SPEC.md §2 + `idx_projects_group` (R3) + `tasks.external_id` с уникальным индексом (R6). Схема: `app/schemas/.../1.json` (R8) |

## 4. Стратегия переезда из TickTick и обновлённая дорожная карта

**Стратегия «переезд с запасным выходом»** (решение PM): импорт без потерь → пробный период → при необходимости выгрузка обратно в CSV TickTick (TickTick импортирует свою резервную копию; дубли PM снимает удалением задач в TickTick перед загрузкой). Синхронизация с TickTick не делается.

### 4.1. Решения по импорту (по реальной выгрузке PM: 3 399 задач, 145 активных)

| Вопрос | Решение |
|---|---|
| Очистка базы (R5) | Единственное физическое удаление; после очистки пересоздаются «Входящие» |
| Чек-листы | В реальном файле маркеры `▪` (выполнено) / `▫` (нет), строки разделены `\r`; разбираются только у задач `Kind = CHECKLIST`. Markdown `- [ ]` в обычных задачах остаётся текстом описания |
| «Весь день» | По колонке `Is All Day` (в `Due Date` время есть всегда); дата — в часовом поясе задачи из колонки `Timezone` |
| Статусы | `0` → активна, `2` и `1` → выполнена, `-1` → **отменена** (отдельный статус) |
| Интервалы времени | `Start Date` хранится в `tasks.start_date`; `Due Date` остаётся сроком |
| Подзадачи | `parentId` → `tasks.parent_id`; удаление родителя удаляет подзадачи |
| Напоминания | Колонка `Reminder` хранится как есть (`tasks.reminders`) до появления уведомлений |
| Остальные поля | Исходная строка CSV целиком хранится в `tasks.source_data` (JSON) — для выгрузки без потерь |
| «Заметки» (`Kind = NOTE`) | Импортируются как обычные задачи (тип сохраняется в `source_data`) |
| Повторы | Правила RRULE хранятся слово в слово; все 39 активных правил PM — стандартные. Режима «после выполнения» у PM нет |
| Порядок | `Order` TickTick → номер позиции внутри списка (1, 2, 3…) |
| Дата создания | Из `Created Time` |

### 4.26. Итог Итерации 23 — уведомления и их значки (0.23.0)

Решения PM (обсуждение на холсте макетов):

- **Готовые напоминания.** Со временем: во время, за 30 минут, 1 час, 1 день, 3 дня. Без времени (только дата):
  10:00, 13:00, 16:00, 19:00, 22:00 в день срока, за 1 и 3 дня в 10:00. «За 5 минут» и «за неделю» убраны
  из меню; у старых задач они продолжают работать и показываются как заданные вручную.
- **«Вручную…»** — окно со счётчиками: у задачи со временем — дни, часы и минуты до срока; без времени — за сколько
  дней и во сколько. Внизу — когда именно сработает («Сработает: пт, 23 окт., 12:30»). Запись — формат TickTick
  (`Reminders.timed` / `Reminders.allDay`), выгрузка не меняется.
- **Значок напоминаний** (`ReminderBadge`, вариант PM «А, серый»): колокольчик и серый значок в углу.
  Во время — без значка; «за …» — `30`, `1ч`, `1д`, `3д` справа внизу; время суток у задачи без времени — круг,
  который заполняется по часовой с верхней левой четверти (утро ¼, обед ½, день ¾, вечер — целый, ночь — луна);
  вручную — часики; несколько — число справа вверху. Вокруг значка колокольчик вырезан.
- **Где показан:** плашка виджета, строка задачи в списках и поиске, кнопка напоминаний в шторке (на зелёной кнопке —
  белый колокольчик и белый значок), пункты меню напоминаний (галочка у выбранных — справа).

Техника: `ReminderIconMasks` рисует три белые маски (колокольчик, подложка, знак) и кэширует их; каждая красится
своим цветом. Так один рисунок работает и в Compose, и в Glance, где цвет светлой/тёмной темы подставляет система.
Новые токены: `ColorTokens.reminderBadge`, `REMINDER_ICON` (18), `WIDGET_REMINDER_ICON` (20).

**Доработка 0.23.1 — таймлайн (макет PM «А»).** Убраны стрелка «к задаче», строка «Сегодня, весь день» сверху
и стрелки «Раньше / Позже» (дни листаются свайпом). Внизу — квадратные иконки «Без даты» (перечёркнутый календарь)
и «Без времени» (перечёркнутые часы) в стиле панели шторки и зелёная галочка «Готово» справа.
