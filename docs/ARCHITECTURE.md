## 1. Аудит архитектуры

### 1.1. Схема Room

| # | Статус | Проблема | Решение / правило | Итерация |
|---|---|---|---|---|
| R1 | 🔴 | **Даты «на весь день» в UTC.** `due_date` хранится как UTC-мс. Задача «на 13 октября, весь день», сохранённая как полночь по Москве, в другом часовом поясе окажется 12-м или 14-м числом. Спецификация не говорит, *какой* момент времени хранить для all-day. | All-day: хранить полночь календарной даты **в UTC** («плавающая» дата) и сравнивать по календарной дате. Задачи с временем: реальный момент времени (UTC), сравнение по локальной дате пользователя. Всё сравнение дат — в одном классе `DayBoundaries`. | 02 |
| R2 | 🟠 | **Мягкое удаление ломает каскад.** `ON DELETE CASCADE` не срабатывает при `is_deleted = 1`. Удалили список — его задачи остаются «живыми» и всплывают на экране «Все» и в виджете. | Удаление списка/папки — одна транзакция, помечающая `is_deleted` у всех потомков (папка → списки → задачи → пункты). FK оставляем с `RESTRICT`/`NO ACTION` как страховку от «сирот». | 02 |
| R3 | 🟠 | **Нет индекса на `projects.group_id`.** Room выдаст предупреждение (FK-колонка без индекса) и будет сканировать таблицу целиком. | Добавить `idx_projects_group ON projects(group_id, is_deleted)`. `tasks.project_id` и `checklist_items.task_id` уже покрыты существующими индексами. | 02 |
| R4 | 🟠 | **Системный «Inbox» никто не создаёт** и ничто не гарантирует, что он один. Импорт из TickTick создаст второй Inbox. | Создавать Inbox при первом создании БД (callback) с фиксированным ID. Импорт «Inbox» → сливаем в существующий, а не создаём новый. | 02, 03 |
| R5 | 🔴 | **Противоречие:** «физическое удаление запрещено» vs кнопка «полная очистка базы» в Настройках. | Предложение: очистка — единственное разрешённое физическое удаление (пока нет синхронизации), после очистки пересоздаётся Inbox. Нужно подтверждение PM. | 03 |
| R6 | 🟠 | **Повторный импорт = дубликаты.** UUID генерируются заново, повторная загрузка того же CSV удвоит задачи. | Вариант А (рекомендую): колонка `external_id` (TickTick `taskId`) + пропуск уже импортированных. Вариант Б: предупреждение «сначала очистите базу». | 03 |
| R7 | 🟡 | «Сегодня» вычисляется в момент запроса. Если экран открыт через полночь — секции не пересчитаются. | Поток «текущий день» (`TodayTicker`), который переключается в полночь и перезапускает запросы. | 04 |
| R8 | 🟡 | Room-схема должна экспортироваться с первого дня, иначе миграции для v1.1 (теги, синхронизация) будут писаться вслепую. | `exportSchema = true`, папка `app/schemas` в git. | 02 |
| R9 | 🟡 | `updated_at` должен меняться при *любом* изменении, иначе синхронизация v1.1 потеряет правки. | Обновление метки — только в репозитории через общий `Clock`, не в UI. | 02 |

### 1.2. Импорт TickTick (замечания к разделу 6)

| # | Статус | Проблема | Решение |
|---|---|---|---|
| I1 | 🟠 | В реальных выгрузках TickTick перед строкой заголовков обычно идут служебные строки (дата экспорта, версия, легенда статусов). | Парсер ищет строку заголовков, а не берёт первую строку файла. |
| I2 | 🟠 | В выгрузке TickTick есть отдельные колонки `Is All Day`, `Timezone`, `Repeat`, `Is Check list`, `parentId`. Спецификация определяет all-day «по наличию времени» — это ненадёжно. | Использовать `Is All Day` и `Timezone`; `Repeat` сразу класть в `rrule` (поле уже есть). |
| I3 | 🔴 | Формат чек-листов `- [ ]` / `- [x]` не подтверждён реальным файлом; вложенные подзадачи TickTick (`parentId`) в схеме не предусмотрены. | Нужен обезличенный пример CSV от PM. Подзадачи с `parentId` → превращать в пункты чек-листа родителя (предложение). |

### 1.3. Навигация и экраны

| # | Статус | Проблема | Решение |
|---|---|---|---|
| N1 | 🔴 | **Нет экрана содержимого списка.** Экран «Списки» показывает папки и списки, но что открывается по тапу на список — не описано. Также нет сценариев переименования/удаления/выбора цвета списка. | Предложение: экран «Задачи списка» в стиле «Входящих» + меню «Переименовать / Цвет / Удалить». Нужно подтверждение. |
| N2 | 🟠 | Контракты маршрутов не описаны. | Типобезопасные маршруты (см. §2.4). |
| N3 | 🟠 | Открытие задачи из виджета: приложение может быть закрыто или уже открыто на другом экране; «Назад» должно вести на «Все», а не закрывать приложение. | Единая точка входа диплинков в `MainActivity` (`onCreate` + `onNewIntent`), стек «Все → Задача». |
| N4 | 🟡 | Опечатка: чип приоритета «P0, P1, P2, P5» — в таблице дизайн-системы P0–P3. | Считать P0–P3 (значения в БД 0/5/3/1). |
| N5 | 🟡 | Правило «Входящих»: `is_inbox = 1` **или** `due_date IS NULL` — задача без даты из списка «Работа» попадёт во Входящие. Это отличается от TickTick. | Подтвердить, что это намеренно (иначе задачи без даты нигде не видны на «Все»). |
| N6 | 🟠 | **Undo 2.5 с**: если ждать 2.5 с перед записью в БД, то при сворачивании приложения отметка потеряется, а виджет обновится с опозданием. | Записываем `status = 2` **сразу**; UI держит карточку видимой 2.5 с (локальное состояние «недавно выполненные»); Undo возвращает `status = 0`. |

### 1.4. Виджет Jetpack Glance

| # | Статус | Проблема | Решение |
|---|---|---|---|
| W1 | 🔴 | **Glance не видит тему приложения.** Glance — отдельная среда отрисовки (RemoteViews), `LocalAppColors` и `MaterialTheme` приложения там не работают. Без подготовки токены придётся дублировать. | Токены — чистые Kotlin-константы без зависимости от Compose (`designsystem/tokens`), из которых строятся два адаптера: `AppTheme` (приложение) и `WidgetTheme` (Glance `ColorProvider` день/ночь). Закладываем в Итерации 01. |
| W2 | 🟠 | Room-Flow не обновляет виджет сам по себе. | `WidgetUpdater.refresh()` после каждой записи в репозитории задач. |
| W3 | 🟠 | В полночь «Сегодня» на виджете устаревает. | Ежедневное обновление в 00:00 (WorkManager). |
| W4 | 🟠 | «Мгновенно» — Android перерисовывает виджеты асинхронно, задержка обычно доли секунды, но не ноль. | Запись в БД — сразу в обработчике клика; перерисовка — сразу после. Формулировку DoD трактуем как «без открытия приложения». |
| W5 | 🟡 | Обработчик клика виджета работает без UI → нужен доступ к репозиторию вне Activity. | DI (Hilt) с `EntryPoint` для виджета. |

## 2. Структура проекта

### 2.1. Модули

MVP — один Gradle-модуль `:app` со строгими пакетами. Изоляция токенов дополнительно защищается автоматической проверкой сборки (`checkDesignTokens`): HEX-цвета (`Color(0x…)`, `#RRGGBB`) вне `designsystem/tokens` валят сборку. Многомодульность (`:core:designsystem`, `:data`, …) — не раньше v1.1, когда появится синхронизация.

### 2.2. Пакеты


### 2.3. Правила зависимостей

```
            ┌──────────────────────────┐
            │  designsystem/tokens     │  (чистый Kotlin)
            └────────┬────────┬────────┘
                     │        │
        ┌────────────▼──┐  ┌──▼─────────────┐
        │ designsystem/ │  │ widget/theme   │
        │ theme (Compose)│ │ (Glance)       │
        └──────┬────────┘  └──┬─────────────┘
               │              │
          ┌────▼────┐    ┌────▼────┐
          │   ui    │    │ widget  │
          └────┬────┘    └────┬────┘
               │              │
               └──────┬───────┘
                      ▼
                ┌──────────┐
                │  domain  │  ◄──── data (реализует интерфейсы)
                └──────────┘
```

- `domain` ни от чего не зависит.
- `ui` и `widget` не знают про `data` (только через интерфейсы `domain`, связывает Hilt).
- `ui` и `widget` не импортируют `designsystem/tokens` напрямую — только через свою тему.

### 2.4. Контракты навигации (предварительно)

| Маршрут | Аргументы | Источник |
|---|---|---|
| `Inbox`, `All`, `Lists`, `Settings` | — | нижний бар (стартовый — `All`) |
| `ProjectTasks` | `projectId: String` | тап по списку на «Списки» (см. N1) |
| `TaskDetail` | `taskId: String` | карточка задачи, виджет |
| `QuickAdd` | `projectId: String?`, `presetDate: Long?` | FAB `[+]`, кнопка `[+]` виджета |

Диплинки виджета: `tasks://task/{taskId}`, `tasks://quickadd`.

```
     ▲                       │
```

## 3. План Итерации 01 — «Инициализация и тема»

**Цель:** `./gradlew assembleDebug` проходит, приложение запускается и показывает пустой экран-витрину с токенами (фон, текст, 4 плашки приоритетов) в светлой и тёмной теме.

| Шаг | Что делаем | Результат |
|---|---|---|
| 0 | Установка Android SDK (command-line tools, platform, build-tools) в среду сборки; JDK 17 toolchain | Можно собирать в облачной среде |
| 1 | Каркас Gradle: `settings.gradle.kts`, корневой `build.gradle.kts`, `gradle.properties`, Gradle Wrapper | `./gradlew` работает |
| 2 | Каталог версий `gradle/libs.versions.toml` — все версии в одном файле, только стабильные релизы | Единая точка обновления зависимостей |
| 3 | Модуль `:app`: `minSdk 29`, актуальные `compileSdk`/`targetSdk`, Kotlin 2.x + плагин Compose-компилятора, KSP (для Room и Hilt) | Модуль собирается |
| 4 | Зависимости: Compose BOM, Material 3, Activity Compose, Lifecycle/ViewModel Compose, Navigation Compose + kotlinx-serialization, Room (runtime/ktx/compiler через KSP), Glance AppWidget + Glance Material 3, Hilt (+ hilt-navigation-compose), WorkManager, Coroutines; тесты — JUnit, kotlinx-coroutines-test, Turbine, Room testing | Все библиотеки подключены, сборка зелёная |
| 5 | Настройка Room-схем: каталог `app/schemas` (без сущностей — они в Итерации 02) | Готово к миграциям |
| 6 | `designsystem/tokens` + `designsystem/theme`: `AppTheme`, `LocalAppColors`, `LocalAppSpacing`, `LocalAppShapes`; светлая/тёмная; динамические цвета выключены; edge-to-edge | Изоляция токенов работает |
| 7 | `widget/theme/WidgetTheme` из тех же токенов (без самого виджета) | Доказано, что Glance переиспользует токены |
| 8 | `TasksApp` (Hilt) + `MainActivity` + экран-витрина токенов | Пустой экран «с правильными цветами» |
| 9 | Gradle-задача `checkDesignTokens`, подключённая к `check` | Хардкод цвета вне токенов валит проверку |
| 10 | (Опционально) GitHub Actions: `assembleDebug` + `check` на каждый push, APK как артефакт сборки | PM может скачать APK без Android Studio |
| 11 | Проверка: `./gradlew assembleDebug check`, коммит, push | Критерий Итерации 01 выполнен |
